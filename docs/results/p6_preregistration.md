## 절차와 한계

1. 기준 숫자는 `docs/EVAL.md` 그대로이고 이 문서는 절차 세부만 추가한다. 결과가 기준에 못 미쳐도 그대로 보고한다.

2. E2는 "한 에이전트 대 한 시스템" 비교다. 두 팔은 생성 모델(gpt-6.1-terra, reasoning_effort low), 도구 집합, 그래프, API 호출 재시도·구조화 교정 한도, 도구 호출 한도, 요청당 텍스트 비용 상한이 같다. Supervisor 팔은 요청 해석, 리서치 분리, 코드가 만드는 보조 값(pattern_context, available_efficacy, aggregates 검증), 루프 내 평가와 최대 2회 재작업 루프를 시스템으로서 함께 가진다. 단일 팔은 보조 값(pattern_context, available_efficacy)을 받지 않는다. 차이는 시스템 구성 전체의 효과이며 결과 문서에도 그렇게 적는다.

3. 반복 횟수는 요청당 팔마다 2회(요청 20건 × 2회, 같은 요청을 팔마다 2회 실행해 요청별로 평균한다), 쌍 비교 부트스트랩의 단위는 요청이며 10,000회(퍼센타일 95%), 시드는 코드 상수 값, 기준 판정은 CI가 0을 넘는지(하한 > 0)로 한다. 반복은 모델 비결정성의 영향을 줄이기 위한 것이며 판정 기준은 `docs/EVAL.md` 그대로다.

4. E2 채점은 Anthropic sonnet이고 팔 이름을 숨기고 순서를 섞고 시드를 고정하며 루프 내 평가와 다른 루브릭·프롬프트를 쓴다. 사람 "claim 일치" 판정 약 200건은 편향 점검용이며 주 판정이 아니다(1인 라벨링). 사람 claim 일치 판정은 반복 1의 기획안(요청 × 팔)만 대상으로 하며 근거 소재마다 한 행이고 표본이 200행을 넘으면 고정 시드로 뽑는다.

5. E5 "끔"의 정의와 식별자 목록(우회: `trim_handoff`·`tool_result_payload` 이원화·원출력 비전달, 추가 전달: `sv_tool_outputs`를 `raw_tool_outputs` 필드로; 유지: `trim_message`·`_text_data`·`research_payload`·`MAX_ROWS` 표시; 불변: 상수·함수 정의), 입력 토큰은 요청 중 원장 증가분의 `input_tokens` 합이다. E5 (a)는 E2 Supervisor 실행을 재사용하며 같은 코드 커밋·같은 세트 해시·같은 채점 실행일 때만 유효하고 코드 커밋 해시와 사전 등록 커밋 해시를 결과 문서에 적는다. 이력 압축은 이 실험에 넣지 않는다.

6. E3: 코퍼스 필드(`CORPUS_FIELDS`), top-k(`TOP_K`), 문서 길이 자르기(`MAX_DOC_CHARS`), 답 프롬프트 버전(`ANSWER_PROMPT_VERSION`), 청크 방식(청크 분할 없음), 임베딩 모델과 선택 기준(dev 질문 hit@k 최고, 동률이면 저가)이 고정이다. 정답은 그래프 질의로 계산해 사람이 확인했다(그래프에 유리한 질문일 수 있다). 코퍼스에 test 브랜드 소재가 섞인다. 질문 37건과 단순 검색형 10건 부분집합을 따로 보고한다.

7. 격리: 4경로·경로당 50건·합계 200건, 표식 문자열 검색을 코드가 판정, 노출 0건 기준, 정상 요청 응답률을 짝 지표로 보고한다. 경로 3은 "다른 테넌트의 thread_id 요청 거부 + 정상 요청 응답 확인"이며 대화 압축 요약 경로는 미구현이라 대상이 아니다. 어디서도 대화 압축 격리를 검증했다고 쓰지 않는다. 재작업 경로(max_reworks=0)는 실행되지 않는다. 요청당 `max_plans=1`, `max_reworks=0`. 0건은 관측값이지 증명이 아니며 시도한 요청 유형의 범위를 결과와 함께 적는다.

8. 층화 보조 분석: 요청·질문의 `axes_used`(세트 확정 때 고정)로 충족 축만 쓰는 항목과 미충족 축(hook_type·angle·talent·has_proof_segment·is_vertical·has_text_overlay·cta_type·claims)을 쓰는 항목을 나눠 따로 보고한다. 결론 근거가 아니며 층의 건수가 작으면 판정 불가로 적는다. 문항은 빼지 않는다. 미충족 축과 claims는 "라벨 신뢰도 낮음(κ x.xx)"로 표시하고 κ 값은 E1 결과 문서에서 그대로 읽는다. 재검사 κ는 재현성 증거로 쓰지 않는다.

9. 동결: 프롬프트 버전·상수·`_SYSTEM` sha256과 세트 해시가 위 줄과 같을 때만 test 실행(와 격리 최종 실행)이 코드로 허용된다. 동결 뒤 프롬프트·상수·세트를 바꾸지 않는다.

10. E4는 선택이며 11-24까지 구현을 시작하지 못했으면 하지 않는다(11-28까지 나머지 실험이 끝나지 않아도 하지 않는다). 하지 않은 경우 결과 문서에 "미수행"과 이유를 적는다.

11. 이미지 생성은 실험에서 끈다. 모든 사람 판정 수치에 "1인 라벨링"을 병기한다. 건수가 작으면 작다고 적는다. 기준을 못 넘긴 항목·판정 불가 항목도 같은 표에 넣는다. 정정은 기존 문장을 고치지 않고 정정 기록으로만 쌓는다.

12. 비용 상한과 실행 순서: E3, E2, E5, 격리, E4(Anthropic 잔여 $1.5 이상일 때만). 호출 전 공급사별 누적액 검사는 유지한다.

15. E3 관계 질문 후보는 정답이 비었거나 정답 집합 크기가 50을 넘는 질문을 제외했다. CQ-08·CQ-13·CQ-14는 데이터 부재로 항상 빈 정답이라 제외된다. 관계 질문은 소수 CQ 유형의 닫힌 입력 조합에서 만든 것이므로 질문 간 독립이 아니며 결과는 이 템플릿 범위에 한정한다.

16. E3 채택 판정은 기존 완전 일치 기준 그대로이며 set 질문의 부분 점수(F1)는 참고용으로 판정에 쓰지 않는다. 정답 집합 크기 10 이하 대 초과와 실행에 쓴 TOP_K 이하 대 초과로 층화 보고한다(참고용, 채택 판정 없음). 벡터 팔은 TOP_K 문서만 보는 구조적 한계가 있어 이 층 구분이 필요하다. TOP_K와 MAX_DOC_CHARS는 dev 질문의 재현율과 비용을 보고 사용자가 사전 등록 전에 확정하며 test 결과를 본 뒤에는 바꾸지 않는다. 임베딩 측정의 hit@k는 정답에서 대응되는 코퍼스 문서(evidence_ids와 문서 id로 대응되는 정답 값)가 있는 질문만 평균하고 대상이 없는 질문 수를 함께 보고한다. 현재 코퍼스 필드에 없는 값(효능·카테고리 값 등)을 정답으로 하는 질문은 벡터 팔이 정의상 도달할 수 없고 이 한계를 결과에 적는다.

17. E3 코퍼스에는 표현 규칙 문서가 포함되며 문서 id는 규칙 ID다. 규칙이 직접 걸리는 대상(APPLIES_TO, 그래프가 적재하는 advisor_approved·confirmed 범위 상태만)만 적고 상속 관계를 미리 펼치지 않는다(상속·범위 추론은 벡터 팔이 직접 해야 한다). 코퍼스에서 도달 가능한 질문만의 부분집합 결과(reachable_subset)는 참고용이며 채택 판정(graph_adopted 등)은 기존 전체 질문 기준이다. 코퍼스에 없는 값(효능·카테고리 값 등)을 정답으로 하는 질문은 도달 불가라는 한계로 적고 도달 가능 질문 수를 함께 보고한다.

18. E5 판정은 `docs/EVAL.md` 그대로 요청당 입력 토큰 합계가 켬이 끔보다 30% 이상 적고 근거 유효율 차이의 95% 신뢰구간 하한이 -0.05보다 커야 하며 둘 중 하나라도 못 넘으면 넘지 못한 쪽을 그대로 적는다. 목적별 입력 토큰(특히 기획 호출)을 요청 단위로 합산한 값은 참고용 보조 지표이며 판정에 쓰지 않는다. 리서치 호출 수가 실행마다 달라 합계가 수천 토큰 흔들릴 수 있다. 예상 결과: 리서치·평가 호출이 입력 토큰의 대부분이고 도구 결과가 작아 합계 기준 30% 감소를 달성하지 못할 가능성이 높으며 그 경우 결과는 토큰 기준 미달로 그대로 보고한다(dev 스모크 2건에서 기획 호출 입력은 끔이 켬보다 약 70% 많았으나 요청당 합계 차이는 거의 없었다는 dev 관찰).

19. E2·E5의 주 판정은 기획안을 시도했으나 내지 못한 경우(근거 없음·실패·한도·범위 밖)를 최저점(요청 적합성 1점, 차별성 1점, 근거 유효율 0)으로 포함해 계산한다. 실행되지 않은 항목(기록 없음)은 제외하고 건수를 보고한다. 기획안이 있는 쌍만 쓰는 완전 사례 분석을 민감도로 함께 보고하며 두 판정이 다르면 그대로 적는다. 팔별 기획 실패율을 보고한다. 채점 실패로 점수가 없는 항목은 팔의 실패가 아니므로 그 지표에서 제외하고 건수를 적는다. 우리 요청은 전부 지원 범위 안이므로 범위 밖(`out_of_scope`) 분류도 실패로 센다.

20. 반복마다 따로 채점하며 팔 이름 숨김·순서 섞기·고정 시드를 유지하고 숨김 id에 반복 번호를 반영한다. 최저점 규칙은 반복 단위로 먼저 적용한 뒤 요청별로 평균한다. 한 팔의 반복이 일부만 없으면 있는 반복만 평균하고 어느 팔이든 반복이 하나도 없으면 실행되지 않은 항목으로 센다. E5 입력 토큰은 요청별 반복 평균이고 E5 (a)는 E2 Supervisor의 두 반복을 모두 재사용한다(같은 코드 커밋·세트 해시·채점 실행). E3와 격리는 반복하지 않는다.

21. EVAL.md 대비 변경: test 질문 40→37(관계 30→27, 단순 검색 10 유지). 사유: CQ-04 count 질문 10건은 정답이 항상 1(결과 행 수)이라 정보가 없어 제외했고, 닫힌 입력 조합을 모두 계산해도 유효한 관계 질문이 27건이다. 단순 검색 10건 비율은 유지하며 요청 20건·dev 구성은 불변이다. 질문 37건이 20건 이상이므로 판정 불가 하한은 해당하지 않는다.

22. 변경 기록: 해석 프롬프트(2026-11-19-1)·닫힌 값 대응표 payload·pattern_context의 지정 축 제외는 P5 이후 변경이며 근거는 dev 스모크 관찰이다. 사용자가 포맷·훅·앵글을 지정해도 해석 결과 brief의 해당 축이 비어 있었고 기획 단계에 지정 값이 전달되지 않았다. P5 dev 비교 증거는 불변인 기획·평가 프롬프트에 대한 것이고 해석 단계는 P5에서 동결 대상이 아니었다. 해석 프롬프트 버전·_SYSTEM·대응표 해시는 이번에 동결 줄에 추가한다.
