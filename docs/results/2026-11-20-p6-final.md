## 3. 사후 진단

아래는 결과를 본 뒤의 분석이며 사전 등록 판정을 바꾸지 않는다.

### 3.1 E2: 격차가 효능 불일치 요청에 몰렸다 (사후 진단)

요청 문장을 보고 사후에 나눴다. 효능이 test 브랜드 제품과 맞는 요청 8건과 맞지 않는 요청 12건이다.

| 요청 적합도 평균 | Supervisor | 단일 | 끔 |
|---|---|---|---|
| 효능이 맞는 8건 | 3.94 | 3.88 | 4.12 |
| 효능이 맞지 않는 12건 | 2.29 | 3.12 | 2.46 |

격차는 효능이 맞지 않는 쪽에 몰린다. 원인은 두 가지로 본다.

- (a) **요청 구성의 한계**: test 요청을 카테고리×효능으로 기계적으로 조합해, 제품이 뒷받침하지 못하는 효능 요청이 섞였다.
- (b) **기획 프롬프트의 설계 한계**: 기획 프롬프트가 `claimed_efficacy`를 코드가 확인한 효능으로 제한한다. 그 결과 요청 효능을 근거 있는 다른 효능으로 바꾸거나 비웠고, 경고는 없었다.

효능 명시 비율(실행 단위, 2회 반복):

| 요청 | 방식 | 요청 효능 명시 | 근거 있는 다른 효능 | 비움 |
|---|---|---|---|---|
| 효능이 맞는 16회 | Supervisor | 14 | – | 2 |
| | 단일 | 8 | – | 8 |
| | 끔 | 14 | – | 2 |
| 효능이 맞지 않는 24회 | Supervisor | 0 | 17 | 7 |
| | 단일 | 0 | 0 | 24 |
| | 끔 | 0 | 12 | 12 |

- 모든 방식이 내세운 효능은 `sun_protection`(35)과 `hydration`(34) 둘뿐이다.
- 코드 검사의 근거 부족 관찰은 모든 방식에서 0건이다.
- **안전성 차이는 측정되지 않았다.** 어느 방식이 더 안전하다는 결론은 이 결과로 내지 않는다.

### 3.2 E3: 비교 구성의 한계 (사후 진단)

- 도구는 `top_rows` 5행, 값 200자 절단, 증거 ID 10개로 결과를 제한한다.
- 정답 URL이 200자를 넘는 질문이 25/37이다.
- CQ-11은 조회 도구가 없다(그래프 0/9, 벡터 4/9).
- 5행 제한이 걸리지 않는 4건에서는 그래프 2/4, 벡터 0/4다.
- 정답이 그래프 질의로 계산된 값이라, 전체 결과를 열면 그래프가 유리해지는 구조다.

결론: 사전 등록 구성에서는 그래프의 검색 정답률 우위를 입증하지 못했다. 비교 구성의 한계 때문이며 그래프가 열세임을 뜻하지 않는다. 온톨로지는 설계 전제이므로 설계 판단에는 영향이 없다.

### 3.3 E5: 토큰 감소가 작은 이유 (사후 진단)

기획 호출 입력은 켬이 끔보다 32% 적다(173,813 대 256,301 토큰). 그러나 리서치·평가 호출이 입력 토큰의 대부분을 차지해, 합계 감소는 7%에 그쳤다. 평가 호출은 오히려 켬이 10.9% 많다.

효능 근거 없이 작성한 기획안은 신뢰할 수 없다는 사용자 결정에 따라 조회 실패·제품 미등록·확인 효능 0개에서는 기획을 진행하지 않거나 되묻는다(이슈 #55).
