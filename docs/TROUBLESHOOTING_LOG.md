# 문제·해결 기록

개발 중 실제로 부딪힌 문제를 그때그때 적는다. 포트폴리오의 "부딪힌 문제와 해결", "회고"는 여기서 고른다.

규칙:
- 실제로 일어난 일만 적는다. 일어날 것 같은 일, 남의 사례는 적지 않는다.
- 결과에는 확인한 값과 확인 방법을 적는다. 확인하지 못했으면 "미확인"이라고 적는다.
- 해결이 안 됐으면 안 된 채로 적는다.

형식: 날짜 / 문제 / 원인 / 해결 / 결과 / 근거

---

## 2026-11-11 브랜드 채널을 검색으로 찾았더니 엉뚱한 채널이 잡혔다
- **문제**: YouTube 검색으로 브랜드 채널을 찾자 8곳 중 3곳이 틀렸다(판매점 채널, 구독자 10명짜리 동명 채널, 해외 유통사 채널).
- **원인**: 채널 검색은 이름이 비슷한 채널을 돌려줄 뿐 공식 여부를 알려주지 않는다.
- **해결**: 브랜드 공식 사이트에 걸린 링크의 채널 ID와 대조해 목록을 고정했다(`config/sources.yaml`, 확인 방법을 계정마다 표기).
- **결과**: YouTube 17채널, Instagram 22계정 확정. Instagram은 추측한 계정 이름 2개가 존재하지 않았고 사이트 링크로 바로잡았다.
- **근거**: `config/sources.yaml`의 `verified` 값.

## 2026-11-12 TikTok 토큰은 발급되는데 광고 조회가 401로 거부됐다
- **문제**: 클라이언트 키·시크릿으로 토큰 발급은 200으로 성공했지만, 광고 조회와 다른 연구 API가 모두 `access_token_invalid`로 거부됐다. 60초까지 기다려 다시 보내도 같았다.
- **원인**: 승인된 연구용 클라이언트는 개발자 포털의 My research에 따로 생기는데, Manage apps에서 앱을 새로 만들어 그 키를 썼다. 다른 앱의 키로도 토큰 발급은 되기 때문에 "토큰은 정상, 조회만 거부"라는 헷갈리는 증상이 나왔다.
- **해결**: 공식 시작 가이드를 읽고 My research의 클라이언트 키로 바꿨다. 처음 안내가 문서를 읽지 않은 추측이었던 것이 시간을 쓴 이유다.
- **결과**: 조회 성공. 브랜드 14곳 모두 광고가 나왔다.
- **근거**: `docs/CONTRACTS.md`의 TikTok 절, `tests/fixtures/contracts/tiktok_*.json`.

## 2026-11-12 TikTok 조회가 날짜 형식과 기준일 때문에 400으로 거부됐다

- **해결**: 문자열 날짜, 끝 날짜는 어제 이전으로 바꿨다. 두 오류 응답을 원본으로 남겼다.
- **결과**: 조회 성공.
- **근거**: `tiktok_error_date_as_number.json`, `tiktok_error_date_max_not_before_today.json`.

## 2026-11-12 상세 이미지에서 뽑은 가격이 실제 가격과 달랐다
- **문제**: 코스알엑스 상세 이미지를 Gemini로 읽었더니 가격이 "16,000원"으로 나왔다. 같은 페이지 메타 태그의 정가는 46,000원, 판매가는 31,000원이었다.
- **원인**: 이미지 안의 행사·할인 문구를 가격으로 읽은 것으로 보인다(미확인). 시험한 상품이 1+1 세트이기도 했다.

- **결과**: 설계만 했고 구현 전이다.
- **근거**: `docs/CONTRACTS.md`의 공식몰 상세페이지 절.

## 2026-11-12 식약처 기능성 보고 정보와 상세페이지의 기능성 표기가 맞지 않았다
- **문제**: 상세페이지에 "주름개선 / 미백 기능성 제품"이라고 적힌 세럼이 식약처 보고품목정보에 있었지만 `EFFECT_YN1`~`3`이 모두 `N`이었다.
- **원인**: 필드의 뜻을 추측(미백·주름·자외선 여부)으로 정했다. 실제 뜻은 확인하지 않았다.
- **해결**: 필드 뜻을 포털 명세로 확인하기 전까지 기능성 판정에 이 필드를 쓰지 않는다. 계약 문서의 추측 문장을 "미확인"으로 바꿨다. 이후 포털 명세에서 `EFFECT_YN1`~`3`이 "2호효능효과_미백/주름개선/자외선"으로 다른 구분임을 확인하고, 기능성 종류는 `EE_NAME`으로 판정하기로 했다.
- **결과**: 표본(코스알엑스 세럼)에서 `EE_NAME`이 "피부의 미백에 도움을 준다. 피부의 주름개선에 도움을 준다."로 상세페이지 표기와 맞았다. 브랜드 3곳 표본에서만 확인했고 전체 품목은 미확인.


## 2026-11-12 Gemini 무료 등급 일일 한도를 재시도로 소진했다
- **문제**: `gemini-3.6-flash` 실측 중 503과 429가 번갈아 났고, 고정 간격으로 재시도를 반복하다 당일 한도가 바닥났다. 429 본문은 "limit: 20 requests per day on Free Tier", 헤더 `retry-after`는 15555초(약 4시간 20분)였다.
- **원인**: 무료 등급의 일일 한도가 하루 20회로 작았고, 503으로 끝난 요청도 한도에 셈된 것으로 보인다(집계 방식은 미확인). 429를 분당 한도처럼 보고 재시도했다.
- **해결**: Gemini 키를 유료 등급으로 전환했다(사용자, 2026-11-12). 래퍼 규칙으로 일일 한도 429는 재시도하지 않고 배치를 멈추도록 정했다(`AGENTS.md`).
- **결과**: 유료 전환 뒤 `gemini-3.6-flash` 직접 호출 4건과 LiteLLM SDK 2건이 모두 200이었다. 래퍼 구현은 아직 없어 규칙의 효과는 미확인.
- **근거**: `tests/fixtures/contracts/gemini_error_free_tier_daily_limit.json`, `docs/CONTRACTS.md`의 Gemini 절.

## 2026-11-12 P1 머지 직후 main에서 make verify가 실패했다
- **문제**: P1 PR을 머지한 직후 main에서 `make verify`가 ruff I001(import 정렬) 6건으로 실패했다(`tests/test_analysis.py`, `test_domain.py`, `test_ledger.py`, `test_sources_config.py`, `test_store.py`, `test_youtube.py`). 같은 코드를 머지 전 브랜치에서 돌렸을 때는 648개 통과였다.
- **원인**: ruff 0.17.4는 기본 규칙에 import 정렬이 들어 있고 `beautyads`를 first-party로 분류하면 Codex가 쓴 테스트의 import 순서(third-party와 한 블록)가 어긋난다. 브랜치에서는 `.ruff_cache`가 이전 결과를 가려 통과로 보였고 `--no-cache`로는 실패했다. first-party 분류가 설정에 고정돼 있지 않았다. 실행기(`execute.py`)가 step마다 돌린 검증이 왜 통과했는지는 확인하지 못했다(미확인).
- **해결**: `pyproject.toml`에 `[tool.ruff.lint.isort] known-first-party = ["beautyads"]`를 추가하고 `ruff check --fix`로 import 순서만 정렬했다(PR #20, 동작·단언 변경 없음).
- **결과**: 수정 뒤 main에서 `ruff check . --no-cache`가 통과하고 `make verify` 648개 통과를 확인했다.
- **근거**: PR #20, 이슈 #19.


## 2026-11-12 Instagram 앱 사용량을 과소추정해 수집이 중간에 멈췄다

## 2026-11-12 재조회 스캔이 사용량으로 중단됐는데 "URL 없음"으로 확정됐다

## 2026-11-13 pilot-compare 제외 규칙이 분석 파이프라인과 달라 정상 항목을 제외했다
- **문제**: 시범 비교의 첫 출력에서 20건 중 6건이 "hook·full 작업 없음"으로 제외돼 n이 14가 됐다.
- **원인**: 사전 등록 §4가 "모델이 `product_creative`로 본 항목의 hook·full이 done이 아니면 제외"로 적혔지만, 파이프라인은 `product_creative`이면서 category가 `other`가 아닐 때만 hook·full을 만든다. 파이프라인 동작을 확인하지 않고 규칙을 썼다(FP-C06과 같은 뿌리).
- **해결**: 제외를 "존재하는 작업이 done이 아님" 또는 "`is_product_target`인데 hook·full이 없음"으로 한정하고(c802cbc), category `other`는 분석 제외로 따로 센다. 사전 등록 §4에 날짜 있는 정정 기록을 남겼다. `is_product_target`과의 일치를 모든 조합에서 검사하는 테스트를 추가했다.
- **결과**: 정정 뒤 n=20. 정정 전 출력의 일치율은 어떤 결정에도 쓰지 않았다.
- **근거**: `docs/results/e1_preregistration.md` §4, `docs/results/2026-11-15-p3-live.md`.

## 2026-11-14 Gemini 크레딧 소진(HTTP 402)이 소재 실패로 기록됐다
- **문제**: YouTube 전체 분석 중 모든 호출이 402로 거절됐는데 `LLM_FATAL`로 분류돼 소재 118건이 실패로 기록됐다. 이어 `--retry-failed`의 반복 실패 규칙으로 90건이 영구 실패로 오기록됐다.
- **원인**: 계정 상태인 장애를 소재의 오류 코드로 기록했고, 새 재시도·영구 제외 규칙이 장애성 오류를 거르는지 확인하지 않았다. 실패 사유도 남기지 않았다.
- **해결**: `ErrorKind.CREDITS_DEPLETED`로 배치를 멈추고 소재는 대기로 둔다(7719803, 811a01b). 분류되지 않은 실패는 마스킹한 사유를 로그에 남긴다. 오기록은 DB에서 수동 복구했다. FP-C07로 기록했다.

## 2026-11-15 `make live-graph`의 표본 50건이 라벨 없는 소재라 분류 축 관계를 검증하지 못했다
- **문제**: 첫 `make live-graph`가 `nodes_created 50`, `relationships_created 0`이고 두 번째 적재는 `nodes_created 0`·`relationships_created 0`(노드 수 불변)이었다. 멱등성은 확인됐지만 분류 축 관계(`USES_HOOK` 등)는 한 건도 검증되지 않았다.
- **원인**: `--limit 50`이 갱신 시각 오름차순의 처음 50건을 읽는데, 갱신 시각이 가장 이른 소재는 수집만 되고 분석되지 않은 소재다(읽기 전용 조회: 그 50건 중 완료된 `*@v1` 작업이 있는 소재 0건). 분석된 소재는 작업 갱신 시각이 더 늦어 표본에 들어가지 않았다. 표본이 라벨이 있는 소재를 포함하는지 확인하지 않았다.
- **해결**: 새 `--sample N` 모드를 만들었다. 훅·전체 라벨이 완료된 소재, 그다음 분석 완료 소재, 그다음 오래된 변경 순으로 고르고 **워터마크를 올리지 않는다**(변경 시각이 아닌 순서로 고른 표본으로 워터마크를 올리면 이후 증분 동기화가 오래된 소재를 건너뛴다). `--limit`·`--full`과는 함께 쓸 수 없다(`SYNC_OPTIONS_CONFLICT`). 검증 모드는 요약에 `graph_check`(표본의 라벨 있는 소재 수, 분류 축 관계 수)를 내고, **표본에 분석 완료 소재가 없으면 `GRAPH_VERIFY_NO_LABELED_SAMPLE`, 라벨이 있는데 관계가 0이면 `GRAPH_VERIFY_NO_RELATIONSHIPS`로 실패한다.** `make live-graph`는 `--sample 50 --verify`가 됐다. 테스트를 먼저 썼다.
- **결과**: 해결(오프라인 테스트로 검증, 사용자의 재실행 대기). 기존 단언은 `live-graph` 레시피 문자열 한 곳만 바꿨다.
- **근거**: `src/beautyads/store/sync_source.py`, `src/beautyads/pipeline/sync.py`, `tests/test_sync_source.py`, `tests/test_sync_pipeline.py`.

## 2026-11-15 소규모 상세 추출에서 제품 2개 실패와 식약처 API 오류 중단
- **문제**: 이미지가 잡힌 제품 5개(브랜드 5곳)로 한 첫 Gemini 추출에서 3개가 완료, 2개가 `PRODUCT_DETAIL_FAILED`(Gemini 호출 0회, 추출 0건)였고 실행이 `STOPPED MFDS_API_ERROR`(종료 코드 3)로 멈췄다. 비용은 4호출 $0.0151이고 성분 86개 중 표준명 일치 91.9%(미해결 7)였다. 제품 인증 대조는 3개 모두 `unknown`이다.
- **원인(이후 확인)**: 제품 2개의 실패는 이미지 전용 호스트(`cosrxinc.jpg3.kr` 등)의 `robots.txt`가 404인데 어댑터가 `MALL_ROBOTS_UNREADABLE`로 거부한 것이다(제품마다 이미지 4장 모두, 진단 보강 뒤 `issues`로 확인). 식약처 `MFDS_API_ERROR`는 `provider_code=01`, `http_status=200`, `provider_message=System Error!!`였고 제품 단계가 아니라 광고 소재 성분 대조 단계에서 났다(이 단계는 제품이 모두 끝난 뒤 돈다). 아래 "미확인" 서술은 첫 관측 당시 것이다.
- **원인(첫 관측)**: 미확인. 코드상 `PRODUCT_DETAIL_FAILED`는 이미지를 읽는 모든 시도가 추출에 성공하지 못했을 때이고 개별 이미지의 오류 코드(`MALL_*`·`PRODUCT_IMAGE_*`)는 `issues`에만 담겨 기록에 남지 않는다. `MFDS_API_ERROR`는 식약처 응답 본문의 `resultCode`가 `"00"`이 아닐 때이고 어떤 코드인지는 출력되지 않는다.
- **해결**: (1) 진단 보강(실패 시 이미지·조각 오류 코드를 `issues`에, 식약처 중단 시 `provider_code`·`provider_message`를 `STOPPED` 줄과 `stopped_detail`에 기록). (2) `robots.txt`가 404·410인 호스트는 제한 없음으로 읽도록 어댑터를 고쳤다(401·403·5xx·연결 실패는 계속 거부). (3) 식약처 `provider_code=01`(System Error!!)은 중단이 아니라 항목 단위 일시 오류로 처리한다: 백오프 재시도 3번 뒤 `MFDS_LOOKUP_FAILED`(대기)로 두고 배치를 계속하며, `03`(데이터 없음)은 빈 결과, 계정 수준 코드(20·22·30·31·32)와 연속 20건 실패는 중단한다(`fix:` 커밋, 테스트 먼저). (4) 로봇 리다이렉트·텍스트 전성분·성분 0개 보류는 각각 별도 `fix:` 커밋이다. 이전에는 `resultCode != "00"`이면 모두 시스템 중단이라 제품 추출이 끝난 뒤 광고 대조가 한 건의 일시 오류로 멈췄다.
- **근거**: `src/beautyads/pipeline/products.py`, `src/beautyads/sources/mfds.py`.
