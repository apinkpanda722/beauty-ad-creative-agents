# 문제·해결 기록

개발 중 실제로 부딪힌 문제를 그때그때 적는다. 포트폴리오의 "부딪힌 문제와 해결", "회고"는 여기서 고른다.

규칙:
- 실제로 일어난 일만 적는다. 일어날 것 같은 일, 남의 사례는 적지 않는다.
- 결과에는 확인한 값과 확인 방법을 적는다. 확인하지 못했으면 "미확인"이라고 적는다.
- 해결이 안 됐으면 안 된 채로 적는다.

형식: 날짜 / 문제 / 원인 / 해결 / 결과 / 근거

---

## 2026-11-11 브랜드 채널을 검색으로 찾았더니 엉뚱한 채널이 잡혔다
- **문제**: YouTube 검색으로 브랜드 채널을 찾자 8곳 중 3곳이 틀렸다(판매점 채널, 구독자 10명짜리 동명 채널, 해외 유통사 채널).
- **원인**: 채널 검색은 이름이 비슷한 채널을 돌려줄 뿐 공식 여부를 알려주지 않는다.
- **해결**: 브랜드 공식 사이트에 걸린 링크의 채널 ID와 대조해 목록을 고정했다(`config/sources.yaml`, 확인 방법을 계정마다 표기).
- **결과**: YouTube 17채널, Instagram 22계정 확정. Instagram은 추측한 계정 이름 2개가 존재하지 않았고 사이트 링크로 바로잡았다.
- **근거**: `config/sources.yaml`의 `verified` 값.

## 2026-11-11 같은 영상의 훅 유형이 호출마다 달랐다
- **문제**: 같은 영상이 한 번은 `question`, 한 번은 `problem`으로 분류됐다.
- **원인**: 훅 유형의 정의가 겹쳤다(질문 형식으로 고민을 제시하는 영상). 두 호출의 모델도 달랐다.
- **해결**: 값마다 관찰 가능한 판정 기준을 적고, 겹칠 때의 우선순위를 정했다(`docs/TAXONOMY.md`).
- **결과**: 미확인. 시범 라벨링과 E1에서 축별 일치도로 확인한다.

## 2026-11-12 제품 광고가 아닌 영상이 제품 소재처럼 분류됐다
- **문제**: 목욕탕 협업 팝업 홍보 릴스가 훅 `product_first`, 포맷 `ugc_style`로 분류됐다.
- **원인**: 공식 계정에는 제품 소재 외에 매장·행사 홍보와 브랜드 캠페인이 섞여 있는데, 분류에 "해당 없음"으로 빠질 길이 없었다.
- **해결**: 다른 축보다 먼저 판정하는 콘텐츠 유형 축을 추가하고 제품 소재만 분석하도록 했다.
- **결과**: 미확인. 콘텐츠 유형 선별의 재현율을 E1에서 잰다.

## 2026-11-11 영상 분석 호출이 과부하로 자주 실패했다
- **문제**: Gemini 호출에서 503 오류가 반복됐고, 한 번은 144초가 걸렸으며 한 번은 150초 넘게 응답이 없었다.
- **원인**: 미확인(서비스 쪽 과부하 메시지).
- **해결**: 검증 스크립트에서는 대기 후 재시도와 다른 모델로 넘기기를 넣어 통과시켰다. 파이프라인에는 소재별 작업 상태를 두고 실패한 건을 다음 실행에서 다시 집도록 설계했다.
- **결과**: 설계만 했고 구현 전이다. 실패율은 파이프라인의 운영 지표로 기록한다.

## 2026-11-12 성분으로 제품 라인 이름이 뽑혔다
- **문제**: 성분 항목에 "Hyalu-Cica"(제품 라인 이름)가 들어갔다. 화면의 실제 성분 표기는 Centella였다.

- **해결**: 표준 성분 사전과 대조해 사전에 없는 값은 버리기로 했다.
- **결과**: 설계만 했고 구현 전이다.

## 2026-11-12 TikTok 토큰은 발급되는데 광고 조회가 401로 거부됐다
- **문제**: 클라이언트 키·시크릿으로 토큰 발급은 200으로 성공했지만, 광고 조회와 다른 연구 API가 모두 `access_token_invalid`로 거부됐다. 60초까지 기다려 다시 보내도 같았다.
- **원인**: 승인된 연구용 클라이언트는 개발자 포털의 My research에 따로 생기는데, Manage apps에서 앱을 새로 만들어 그 키를 썼다. 다른 앱의 키로도 토큰 발급은 되기 때문에 "토큰은 정상, 조회만 거부"라는 헷갈리는 증상이 나왔다.
- **해결**: 공식 시작 가이드를 읽고 My research의 클라이언트 키로 바꿨다. 처음 안내가 문서를 읽지 않은 추측이었던 것이 시간을 쓴 이유다.
- **결과**: 조회 성공. 브랜드 14곳 모두 광고가 나왔다.
- **근거**: `docs/CONTRACTS.md`의 TikTok 절, `tests/fixtures/contracts/tiktok_*.json`.

## 2026-11-12 TikTok 조회가 날짜 형식과 기준일 때문에 400으로 거부됐다
- **문제**: 날짜 범위의 끝을 오늘로 넣자 400, 문서 예시대로 숫자로 넣자 다시 400이 났다.
- **원인**: 날짜는 문자열이어야 하고, 끝 날짜는 오늘보다 앞이어야 한다. 문서 본문과 예시가 서로 달랐다(필드 이름과 타입도 예시와 정의 표가 엇갈렸다).
- **해결**: 문자열 날짜, 끝 날짜는 어제 이전으로 바꿨다. 두 오류 응답을 원본으로 남겼다.
- **결과**: 조회 성공.
- **근거**: `tiktok_error_date_as_number.json`, `tiktok_error_date_max_not_before_today.json`.

## 2026-11-12 상세 이미지에서 뽑은 가격이 실제 가격과 달랐다
- **문제**: 코스알엑스 상세 이미지를 Gemini로 읽었더니 가격이 "16,000원"으로 나왔다. 같은 페이지 메타 태그의 정가는 46,000원, 판매가는 31,000원이었다.
- **원인**: 이미지 안의 행사·할인 문구를 가격으로 읽은 것으로 보인다(미확인). 시험한 상품이 1+1 세트이기도 했다.
- **해결**: 가격은 이미지에서 뽑지 않고 HTML 메타 태그(`product:price:amount`)로만 읽기로 했다. 대표 제품은 단품으로 고른다.
- **결과**: 설계만 했고 구현 전이다.
- **근거**: `docs/CONTRACTS.md`의 공식몰 상세페이지 절.

## 2026-11-12 식약처 기능성 보고 정보와 상세페이지의 기능성 표기가 맞지 않았다
- **문제**: 상세페이지에 "주름개선 / 미백 기능성 제품"이라고 적힌 세럼이 식약처 보고품목정보에 있었지만 `EFFECT_YN1`~`3`이 모두 `N`이었다.
- **원인**: 필드의 뜻을 추측(미백·주름·자외선 여부)으로 정했다. 실제 뜻은 확인하지 않았다.
- **해결**: 필드 뜻을 포털 명세로 확인하기 전까지 기능성 판정에 이 필드를 쓰지 않는다. 계약 문서의 추측 문장을 "미확인"으로 바꿨다. 이후 포털 명세에서 `EFFECT_YN1`~`3`이 "2호효능효과_미백/주름개선/자외선"으로 다른 구분임을 확인하고, 기능성 종류는 `EE_NAME`으로 판정하기로 했다.
- **결과**: 표본(코스알엑스 세럼)에서 `EE_NAME`이 "피부의 미백에 도움을 준다. 피부의 주름개선에 도움을 준다."로 상세페이지 표기와 맞았다. 브랜드 3곳 표본에서만 확인했고 전체 품목은 미확인.


## 2026-11-12 Gemini 무료 등급 일일 한도를 재시도로 소진했다
- **문제**: `gemini-3.6-flash` 실측 중 503과 429가 번갈아 났고, 고정 간격으로 재시도를 반복하다 당일 한도가 바닥났다. 429 본문은 "limit: 20 requests per day on Free Tier", 헤더 `retry-after`는 15555초(약 4시간 20분)였다.
- **원인**: 무료 등급의 일일 한도가 하루 20회로 작았고, 503으로 끝난 요청도 한도에 셈된 것으로 보인다(집계 방식은 미확인). 429를 분당 한도처럼 보고 재시도했다.
- **해결**: Gemini 키를 유료 등급으로 전환했다(사용자, 2026-11-12). 래퍼 규칙으로 일일 한도 429는 재시도하지 않고 배치를 멈추도록 정했다(`AGENTS.md`).
- **결과**: 유료 전환 뒤 `gemini-3.6-flash` 직접 호출 4건과 LiteLLM SDK 2건이 모두 200이었다. 래퍼 구현은 아직 없어 규칙의 효과는 미확인.
- **근거**: `tests/fixtures/contracts/gemini_error_free_tier_daily_limit.json`, `docs/CONTRACTS.md`의 Gemini 절.

## 2026-11-12 단종 상품 주소가 HTTP 200으로 왔다
- **문제**: 믹순 공식몰의 단종 상품 주소(`product_no=552`)가 오류가 아니라 200과 "페이지가 사라졌거나" 안내 HTML(3.4KB)로 응답했다.

## 2026-11-12 P1 머지 직후 main에서 make verify가 실패했다
- **문제**: P1 PR을 머지한 직후 main에서 `make verify`가 ruff I001(import 정렬) 6건으로 실패했다(`tests/test_analysis.py`, `test_domain.py`, `test_ledger.py`, `test_sources_config.py`, `test_store.py`, `test_youtube.py`). 같은 코드를 머지 전 브랜치에서 돌렸을 때는 648개 통과였다.
- **원인**: ruff 0.17.4는 기본 규칙에 import 정렬이 들어 있고 `beautyads`를 first-party로 분류하면 Codex가 쓴 테스트의 import 순서(third-party와 한 블록)가 어긋난다. 브랜치에서는 `.ruff_cache`가 이전 결과를 가려 통과로 보였고 `--no-cache`로는 실패했다. first-party 분류가 설정에 고정돼 있지 않았다. 실행기(`execute.py`)가 step마다 돌린 검증이 왜 통과했는지는 확인하지 못했다(미확인).
- **해결**: `pyproject.toml`에 `[tool.ruff.lint.isort] known-first-party = ["beautyads"]`를 추가하고 `ruff check --fix`로 import 순서만 정렬했다(PR #20, 동작·단언 변경 없음).
- **결과**: 수정 뒤 main에서 `ruff check . --no-cache`가 통과하고 `make verify` 648개 통과를 확인했다.
- **근거**: PR #20, 이슈 #19.
