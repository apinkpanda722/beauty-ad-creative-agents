# Architecture Decision Records

## 철학
도메인 문제(경쟁 소재 분석과 기획)를 먼저 풀고, 기술 선택은 그 문제에서 나온 이유로만 한다. 실데이터와 공개 배포를 전제로 하고, 구조 선택(멀티에이전트, 온톨로지)은 대안과 비교한 수치로 근거를 남긴다. 기준에 못 미친 결과도 그대로 보고한다.

---

### ADR-001: 도메인과 범위
**결정**: 뷰티 광고 크리에이티브 분석과 기획을 다룬다. 카테고리는 마스크팩·세럼/앰플·선케어 3개로 시작한다. 영상 이해는 포함하고 영상 생성은 제외한다.
**이유**: 지원 대상 공고가 요구하는 영역이고, 훅과 포맷은 카테고리 공통이라 3개로 늘려도 분류 비용이 크게 늘지 않는다. 카테고리 간 비교 질문이 생겨 그래프의 쓸모가 커진다. 영상 생성은 에이전트 설계가 아니라 크리에이티브 제작 영역이다.
**트레이드오프**: 현업 마케팅 경험이 없어 분류 기준의 권위가 약하다. 공개된 실무 프레임워크를 출처로 삼고 관찰 가능한 항목으로 한정해 보완한다.

### ADR-002: Supervisor 멀티에이전트
**결정**: Supervisor 아래에 리서치·기획·평가 에이전트를 둔다. 평가에서 기획으로 되돌리는 횟수는 최대 2회다.
**이유**: 만든 쪽과 평가하는 쪽을 분리해야 자기 결과를 스스로 통과시키는 것을 피할 수 있다. 리서치(그래프 탐색)와 기획(생성)은 필요한 도구와 문맥이 다르다.
**트레이드오프**: 단일 에이전트보다 모델 호출과 지연이 늘어난다. 같은 요청을 단일 구성으로도 실행해 품질·비용·지연을 비교한다(E2). 비교 결과와 무관하게 Supervisor 구성을 유지하기로 했고(2026-11-12), 품질 차이를 확인하지 못하면 늘어난 비용과 지연을 대가로 그대로 보고한다. 단일 구성이 더 낫게 나와도 결과는 숨기지 않는다.

### ADR-003: 수집은 에이전트가 아니라 파이프라인
**결정**: 수집은 스케줄 파이프라인으로 만들고, 출처별 어댑터가 공통 소재 형식으로 변환한다.
**이유**: 판단이 필요 없는 정해진 작업이다. 출처가 YouTube·Instagram 둘이고 Meta 광고·TikTok이 승인되면 늘어나므로 어댑터 경계가 필요하다.
**트레이드오프**: 없음에 가깝다. 출처마다 지표의 뜻이 달라(조회수, 도달 수) 공통 형식에서 지표 종류를 구분해 둬야 한다.

### ADR-004: 데이터 출처
**결정**: 1차 범위는 YouTube Data API와 Instagram Graph API(Business Discovery)다. 공식 API만 쓰고 크롤링과 영상 무단 다운로드는 하지 않는다. Meta 광고 라이브러리와 TikTok Commercial Content API는 승인되면 추가한다.
**이유**: 둘 다 첫 호출로 동작을 확인했다(2026-11-11). 뷰티 브랜드의 주력 채널은 Instagram이고(팔로워 규모가 YouTube의 수십 배), YouTube는 영상 분석이 가장 쉽다.
**트레이드오프**: 광고 소재만이 아니라 일반 콘텐츠가 섞인다. 조회수에 광고비 효과가 섞여 성과 해석이 약하다. Instagram 릴스는 표본의 52%만 영상 주소가 반환됐다.

### ADR-005: 모델 배치
**결정**: 영상 분석은 Gemini, Supervisor·리서치·기획은 OpenAI, 평가는 Anthropic(Claude)을 쓴다. 호출은 LiteLLM을 거친다.
**이유**: Gemini는 YouTube 주소를 그대로 영상 입력으로 받아 파일 확보 문제를 피한다. 기획과 평가를 다른 회사 모델로 나눠 자기 채점을 피한다. 프로젝트 B의 LiteLLM 구성을 재사용한다.
**트레이드오프**: 세 회사의 키와 단가를 관리해야 한다. Gemini의 YouTube 주소 입력은 프리뷰 기능이라 가격과 한도가 바뀔 수 있다. 모델 등급은 M0에서 단가를 확인해 정한다.

### ADR-006: 그래프 DB는 Neo4j
**결정**: 온톨로지를 Neo4j에 둔다. 시계열 지표 원본과 체크포인터는 PostgreSQL에 둔다.
**이유**: 카테고리 간 훅 비교처럼 관계를 따라가야 답이 나오는 질문이 핵심 시나리오다. 그래프 화면을 그대로 시연 자료로 쓸 수 있다.
**트레이드오프**: 저장소가 둘이 되어 동기화와 운영 부담이 생긴다. 벡터 검색만 쓴 구성과 정답률을 비교해(E3) 필요성을 수치로 남긴다.

### ADR-007: 로컬 실행, 서버 비용 없음 (2026-11-12 변경)
**결정**: 개발·실험·시연을 모두 로컬에서 한다. 유료 서버에 상시 배포하지 않는다. 비용은 모델 호출만 들고 월 상한은 약 5만 원이다. Kubernetes 매니페스트는 로컬 클러스터(k3d)에서 동작하도록 만든다.
**이유**: 서버 고정 비용이 부담이다. 수집과 영상 분석은 한 번 돌려 그래프에 넣으면 되는 작업이라 상시 서버가 필요 없다. 로컬 클러스터로도 Kubernetes 배포 구성은 남길 수 있다.
**트레이드오프**: 누구나 눌러서 써볼 수 있는 공개 주소가 없다. 시연 영상, 화면 캡처, 명령 한 줄로 띄우는 로컬 실행 절차로 대신한다. 무료 호스팅에 올리는 읽기 전용 재생 데모(저장해 둔 실행 결과와 그래프를 보여주는 정적 페이지)는 M3에서 시간이 남으면 검토한다.
**이전 결정**: 같은 날 "가상 서버 1대 + k3s 공개 배포"로 정했다가 비용 때문에 바꿨다.

### ADR-008: 컨텍스트 관리 — 지시서, 구조화 핸드오프, 이력 압축
**결정**: Supervisor는 하위 에이전트에 과제 지시서만 넘기고, 하위 에이전트는 스키마로 검증되는 구조화 요약으로 돌려준다. 원자료와 도구 원출력은 상태 저장소에 두고 ID로 참조한다. 도구는 전체 결과를 화면으로, 요약을 모델로 나눠 보낸다. 대화 이력은 입력 예산을 넘으면 압축하고, 근거 ID·사용자 조건·피드백은 압축에서 제외한다.
**이유**: 리서치 결과가 소재 수십 건이라 그대로 주고받으면 Supervisor 입력이 원자료로 찬다. 비용과 지연이 늘고 도구 선택이 흐려진다. 하위 에이전트의 컨텍스트를 격리해야 역할을 나눈 의미가 있다.
**트레이드오프**: 요약 과정에서 근거가 빠질 수 있다. 근거 ID를 요약 문장이 아니라 별도 목록으로 넘기고 코드 검사로 대조해 막는다. 핸드오프 형식과 압축 로직만큼 구현과 테스트가 늘어난다. 효과는 원자료를 그대로 넘기는 구성과 비교해 수치로 남긴다(E5).

### ADR-009: 멀티테넌트 — 테넌트는 세션이 정하고 도구가 범위를 건다
**결정**: 테넌트를 한 회사 안의 브랜드별 작업 공간으로 둔다. 데모에는 2개를 둔다. 공개 소재 분석은 공용, 브랜드 프로필·기획안·피드백·대화 이력·압축 요약은 테넌트 전용이다. `tenant_id`는 세션에서만 나오고 도구 입력에는 넣지 않는다. 모든 도구가 호출 전에 실행 컨텍스트의 `tenant_id`로 범위를 걸고, 검사 실패 시 거부한다. 관리 경로는 에이전트 도구로 노출하지 않는다.
**이유**: 여러 브랜드를 가진 회사가 공통 기반을 재사용하되 브랜드마다 말투·금지 표현·전략·피드백이 다르다. 피드백 메모리에 쌓인 한 브랜드의 반려 사유가 모델의 혼동이나 프롬프트 인젝션으로 다른 브랜드의 기획안에 섞일 수 있다. 모델의 판단에 맡기지 않고 코드로 막는다. 프로젝트 A·B에서 쓴 "신원은 서버가 주입한다" 원칙을 테넌트로 넓힌 것이다.
**트레이드오프**: 저장소·도구·체크포인터·trace 전부에 테넌트 구분이 들어가 구현과 테스트가 늘어난다. 실제 사용 조직이 없으므로 운영 실적이 아니라 설계와 격리 검사 결과만 보일 수 있다. 같은 회사 안의 격리라 다른 회사 간 격리보다 필요성이 약하게 읽힐 수 있다. 실제 인증과 테넌트 안의 사용자 권한은 범위 밖이다.

### ADR-010: PostgreSQL이 원본, Neo4j는 증분 동기화로 만드는 파생물
**결정**: 수집·분석 결과는 먼저 PostgreSQL에 쓴다. 동기화 작업이 마지막 반영 시점 이후 바뀐 행만 읽어 Neo4j에 반영한다. 반영은 반복해도 결과가 같게 만들고(MERGE), 그래프는 언제든 원본에서 다시 만들 수 있게 한다.
**이유**: 그래프에 직접 쓰면 스키마를 바꾸거나 분류를 고칠 때 되돌릴 방법이 없다. 원본을 따로 두면 분류 v1 동결 뒤에도 재적재로 대응할 수 있고, 지표 이력처럼 그래프에 맞지 않는 데이터를 관계형에 둘 수 있다.
**트레이드오프**: 저장소 둘 사이에 지연과 불일치 구간이 생긴다. 동기화 실패를 감지할 점검(원본 건수와 그래프 노드 수 대조)이 필요하다. 동기화 실행 도구(스케줄러)는 M0에서 정한다.

### ADR-011: 도구는 네 종류로 나누고, 화면에 그릴 것은 모델을 거치지 않는다
**결정**: 그래프 도구를 조회·집계·비교·표시로 나눈다. 도구 설명에 사용 조건과 쓰지 말아야 할 경우를 적고, 실패는 구조화된 실패로 돌려준다. 표시 도구와 그 밖의 도구의 전체 결과는 화면 명령 이벤트로 프런트에 직접 보내고, 모델에는 요약만 준다. 기준일과 테넌트는 서버가 넣고 도구 입력에 두지 않는다.
**이유**: 도구가 늘수록 모델이 잘못 고른다. 종류와 사용 조건을 명시하면 선택이 안정된다. 근거 소재 수십 건을 모델 입력으로 넣으면 비용과 지연이 늘고 정작 화면에는 모델이 다시 써 준 축약본만 나온다. 날짜를 모델에 맡기면 "최근"의 뜻이 호출마다 달라진다.
**트레이드오프**: 프런트가 화면 명령 종류를 알아야 해서 API와 화면이 계약으로 묶인다. 명령 종류를 늘릴 때 양쪽을 함께 고쳐야 한다. 모델은 화면에 그려진 전체 데이터를 보지 못하므로, 화면에는 있는데 답변에는 없는 내용이 생길 수 있다.
