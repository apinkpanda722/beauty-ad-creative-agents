# 실패 패턴

같은 실패를 두 번 겪지 않기 위한 기록이다. 프로젝트 B는 테스트와 live에서 드러난 결함을 고치느라 계획한 PR 3개가 9개로 늘었고, 원인의 대부분은 **구현 전에 확인할 수 있었던 것**이었다. 이 프로젝트는 처음부터 아래 규칙을 step 설계에 넣는다.

항목 번호(FP-NNN)는 이 저장소의 번호다. A·B에서 가져온 항목은 "이식" 절에 `B-FP-NNN`·`A-FP-NNN`으로 적는다. 자세한 증상은 각 저장소의 같은 이름 스킬을 본다(A·B 저장소는 수정하지 않는다).

## 사용법

- **/harness (step 설계)**: 작업과 관련된 항목을 골라 그 step의 `## 금지사항` 또는 `## 작업`에 **이유와 FP 번호를 함께** 옮겨 적는다. Codex는 이 파일을 읽지 않고 step 파일만 읽는다.
- **phase 설계 초안의 필수 항목** (없으면 승인하지 않는다. `/harness` 설계 원칙 12번과 `/review` 체크리스트 10·11번이 확인한다):
  1. **외부 계약 실측 목록**: phase가 의존하는 외부 지점마다 `docs/CONTRACTS.md`의 해당 줄과 원본 경로. 문서에 없는 지점은 먼저 실측해 추가한다. 성공 여부와 반환 내용을 따로 적는다.
  2. **첫 live에서 터질 수 있는 것**: 환경·설정·서비스 기동 상태 목록과 각각을 막는 사전 점검.
  3. **기존 단언과의 충돌 점검**: 이 phase가 만드는 새 파일·새 키·새 이벤트·새 상태가 깨는 기존 테스트 목록(아래 FP-C03 방법).
  4. **머지 뒤 사용자가 할 일과 순서**.
- **/review**: 변경에 아래 패턴이 다시 나타나는지 확인한다. 이번 phase에서 수정 커밋이 있었던 실패는 이 문서에 항목으로 추가하고 `docs/TROUBLESHOOTING_LOG.md`에도 적는다.
- **승격**: 같은 패턴이 두 번째로 나오거나 기계적으로 검사할 수 있으면 테스트로 만들고 강제 수단에 테스트 이름을 적는다.

## 항목 형식

`### FP-NNN 제목` / 증상 / 원인 / 규칙 / 강제 수단 / 출처

## C. 이 프로젝트에서 겪은 것

### FP-C01 외부 서비스의 "없음"과 "오류"가 서비스마다 다른 형태로 온다
- **증상**: 착수 전 실측에서 같은 종류의 상황이 전부 다른 형태였다. YouTube의 없는 핸들은 200에 `items` 키가 아예 없고, Instagram의 없는 계정은 400에 코드 110이고, `media_url`·`view_count`는 없을 때 `null`이 아니라 키가 빠진다. Gemini는 과부하가 객체에 문자열 코드, 잘못된 키가 **배열**에 정수 코드다.
- **원인**: 서비스마다 규칙이 다르고 문서만으로는 알 수 없다.
- **규칙**: 외부 응답을 읽는 코드는 `docs/CONTRACTS.md`에 실측된 형태만 전제한다. 키는 없을 수 있다고 보고 읽는다(`[]` 직접 접근 금지, 없을 때의 동작을 테스트로 정한다). 오류는 HTTP 상태를 먼저 보고 본문은 실측된 모든 형태를 받는다. 픽스처는 `tests/fixtures/contracts/`의 원본에서 만든다.
- **강제 수단**: 어댑터·모델 래퍼의 테스트가 원본 픽스처를 직접 읽는다(구현 시 테스트 이름을 여기에 적는다).
- **출처**: 2026-11-11~12 착수 전 실측, `docs/CONTRACTS.md`

### FP-C02 모델 응답에서 답의 위치를 순서로 가정
- **증상**: 검증 스크립트가 Gemini 응답의 답을 `outputs`에서 찾았는데 실제로는 `steps[]` 안의 `type == "model_output"` 항목에 있었다. 첫 항목은 `thought`였다. "JSON만"을 요구해도 본문은 코드 울타리로 감싸져 왔다.
- **원인**: 응답 구조를 문서 요약으로 추측했다.
- **규칙**: 답은 항목의 `type`으로 찾고 위치(`[0]`, `[-1]`)로 찾지 않는다. 모델 출력을 JSON으로 읽는 코드는 울타리가 있는 경우와 없는 경우를 모두 처리하고, 파싱 실패는 구조화된 실패로 돌려준다. 형식은 프롬프트가 아니라 스키마 검증으로 보장한다.
- **강제 수단**: 모델 래퍼 테스트(원본 `gemini_interactions_*.json` 사용).
- **출처**: 2026-11-11 검증 스크립트 수정

### FP-C03 분류 값이 호출마다 달라지는데 한 번의 출력으로 정답을 굳힘
- **증상**: 같은 영상이 한 번은 `question`, 한 번은 `problem`으로 분류됐다. 제품 광고가 아닌 팝업 홍보 영상이 제품 소재처럼 분류됐다. 성분 칸에 제품 라인 이름이 들어갔다.
- **원인**: 분류 정의가 겹쳤고, 해당 없음으로 빠질 길이 없었고, 열린 목록이었다.
- **규칙**: 모델 출력의 **값**을 테스트 기대값으로 굳히지 않는다. 테스트는 형식(스키마, 닫힌 값 목록 안인지)과 코드가 하는 일(검증, 재요청, 보류 처리)을 검사한다. 모델의 정확도는 테스트가 아니라 평가(E1)에서 잰다.
- **강제 수단**: /review 체크(테스트 기대값에 모델이 생성한 문장·분류 값이 들어 있지 않은가).
- **출처**: 2026-11-11~12 실측, `docs/TROUBLESHOOTING_LOG.md`

### FP-C04 린트 결과가 캐시와 설정 미고정에 따라 달라져 머지 뒤 검증이 깨짐
- **증상**: P1 브랜치에서 통과하던 `make verify`가 머지 직후 main에서 ruff I001 6건으로 실패했다.
- **원인**: ruff 0.17.4의 기본 규칙에 import 정렬이 있고, first-party 분류가 `pyproject.toml`에 고정돼 있지 않았다. `.ruff_cache`가 이전 결과를 가려 브랜치에서는 통과로 보였다.
- **규칙**: 린트·포맷 설정은 결과가 환경과 캐시에 따라 달라지지 않게 `pyproject.toml`에 고정한다(first-party 분류 포함). 머지 전 검증은 캐시 없이(`uv run ruff check . --no-cache`)도 통과해야 한다. 도구 버전이 올라가면 기본 규칙이 바뀔 수 있다고 본다.
- **강제 수단**: `pyproject.toml`의 `known-first-party`(PR #20). 머지 전 `--no-cache` 점검은 /review 체크.
- **출처**: 2026-11-12 P1 머지 직후, `docs/TROUBLESHOOTING_LOG.md`, 이슈 #19

### FP-C05 중단을 "없음"으로 확정
- **증상**: Instagram 재조회 스캔이 앱 사용량으로 1쪽에서 멈췄는데 못 찾은 게시물 3건을 `MEDIA_URL_MISSING`(없음)으로 기록했다. 3건 모두 2쪽 게시물이었다.
- **원인**: "끝까지 찾았는데 없다"와 "찾다가 멈췄다"를 한 결과값으로 합쳤다.
- **규칙**: 탐색·조회가 중간에 멈췄으면 못 찾은 대상은 "없음"이 아니라 "미확정(재시도 가능)"이다. 결과 형식에 중단 여부를 담고(`stopped`), 호출하는 쪽이 둘을 다른 상태로 기록한다. 재시도 가능한 상태는 재시도 경로가 있어야 한다. 새 어댑터(TikTok 재조회)에도 같은 테스트를 요구한다.
- **강제 수단**: `tests/test_media_flow.py`(중단 시 `MEDIA_REFRESH_STOPPED`), `tests/test_pilot.py`(재시도 전용 모드).
- **출처**: 2026-11-12 P2 `make live-pilot`, `docs/TROUBLESHOOTING_LOG.md`

### FP-C06 문서의 추정값을 계획의 근거로 사용
- **증상**: `docs/CONTRACTS.md`에 "호출당 앱 사용량 약 0.5%(실측 추정)"가 있었고 `--dry-run`의 예상값과 수집 계획이 이 값에서 나왔다. 실제는 13계정·약 26호출에서 80%에 닿았다.
- **원인**: 몇 건의 관측에서 나온 추정을 계약 사실처럼 적었고 계획 수치가 그 위에 쌓였다.
- **규칙**: 계획·견적·한도의 근거로 쓰는 숫자는 "실측 건수, 조건, 날짜"가 붙은 값만 쓴다. 추정은 문서에 추정이라고 적고 계획 수치에는 쓰지 않거나 안전 계수를 적어 첫 live의 실측으로 교체한다. live로 값이 틀린 것이 드러나면 계약 문서를 고치고 견적 코드를 같이 점검한다.
- **강제 수단**: /review 체크(계획 수치의 근거가 실측인지 추정인지 구분), `--dry-run` 출력에 "가정(미실측)" 표기 유지.
- **출처**: 2026-11-12 P2 `make live-collect` 1차, `docs/TROUBLESHOOTING_LOG.md`

### FP-C07 시스템 장애를 소재 실패로 기록
- **증상**: Gemini 선불 크레딧이 소진돼 모든 호출이 HTTP 402로 거절됐는데 일반 `LLM_FATAL`로 분류돼 소재 118건이 실패로 기록됐다. 이어 `--retry-failed`가 `LLM_FATAL`을 재시도 대상으로 삼고 "재시도에서도 같은 코드로 실패하면 영구 제외(`LLM_FATAL_REPEATED`)" 규칙을 적용해, 장애가 계속되는 동안 90건이 영구 실패로 오기록됐다(DB는 수동 복구). 충전 뒤 121건이 모두 성공했다.
- **원인**: 크레딧 소진·네트워크·인증 같은 계정·환경 상태를 요청이 틀린 것처럼 소재의 오류 코드로 기록했고, 새 재시도·영구 제외 규칙을 만들 때 장애성 오류가 그 규칙을 타는지 확인하지 않았다. 실패 사유(메시지)를 어디에도 남기지 않아 원인을 사후에 알 수 없었다.
- **규칙**: 시스템 장애(크레딧 소진, 인증, 네트워크, 한도)는 소재 실패로 기록하지 않는다. 배치를 멈추고 소재는 대기 상태로 두며 시도 횟수를 올리지 않는다. 새 오류 코드를 재시도 대상에 넣거나 반복 실패 규칙을 만들 때는 장애성 오류가 그 규칙을 타지 않는지 먼저 확인한다. 분류되지 않은 호출 실패는 사유(마스킹한 메시지)를 로그에 남긴다.
- **강제 수단**: `ErrorKind.CREDITS_DEPLETED`(배치 정지, `tests/test_llm.py`·`tests/test_analyze_runner.py`), `LLM_CALL_FAILED` 사유 로그와 키 마스킹(`tests/test_analysis.py`).
- **출처**: 2026-11-14 P3 YouTube 전체 분석, 커밋 7719803·811a01b

### FP-C08 한 가지 마크업만 남긴 픽스처가 다른 구조의 결함을 못 잡는다
- **증상**: P4 첫 `--scan`에서 상세 이미지를 읽어야 하는 59개 제품 중 24개(4개 몰)가 이미지 0개로 잡혔다. 어댑터는 `#prdDetail`의 `ec-data-src` 이미지만 읽었고, 달바(고도몰)는 이미지가 `#prdDetail` 밖에, 이즈앤트리는 정적 이미지가 없었다. 어댑터 테스트는 모두 통과했다.
- **원인**: 몰마다 마크업이 다른데 픽스처를 만들 때 어댑터가 읽는 요소(`ec-data-src` 이미지)만 남기고 나머지를 잘라 냈고, 코스알엑스·아누아 같은 일부 몰의 원본만 기준으로 삼았다. 같은 가짜로 어댑터와 테스트가 같은 가정을 공유했다(B-FP-020).
- **규칙**: 몰·출처마다 **실제 응답 원본을 최소 1개씩 보관**해 어댑터를 검증한다. 구조가 다른 몰(플랫폼이 다르거나 템플릿이 다른 몰)은 각각 별도 픽스처가 있어야 하고, 픽스처를 줄일 때는 어댑터가 읽는 요소만 남기지 말고 다른 구조의 판별에 필요한 주변 요소(이미지가 없는 경우의 컨테이너 등)를 남긴다. 첫 live 전에 전체 대상을 훑는 읽기 전용 점검(`--scan` 같은)으로 "읽은 값이 0인 항목"을 확인한다. 값이 0인 항목은 오류가 아니므로 결과에 별도 집계한다(B-FP-040).
- **강제 수단**: `tests/test_mall.py`의 몰 구조별 테스트(`test_detail_images_in_a_tab_container_use_plain_src_and_skip_icons`, `test_detail_images_after_an_empty_anchor_extend_past_the_review_anchor`, `test_detail_images_in_a_content_block_use_plain_src`, `test_godomall_detail_section_images_are_read`)가 실제 원본에서 만든 픽스처(`mall_cafe24_tab_src`·`empty_anchor`·`tab_cont`, `mall_godomall_detail`)를 읽는다. /review 체크(몰·출처별 원본 픽스처가 있는가, 픽스처가 어댑터가 읽는 요소만 남기고 잘렸는가).
- **출처**: 2026-11-15 P4 `make live-products --scan`, `docs/TROUBLESHOOTING_LOG.md`

### FP-C09 추출 실패를 데이터 부재로 단정한다 / 재저장이 이전 행을 지우지 않는다
- **증상**: P4에서 바이오던스 제품 5개가 "상세 이미지에 전성분이 없다"며 보류됐고 교체까지 논의됐는데, 저장해 둔 페이지의 본문에 `[전성분] 정제수, …`가 인라인 텍스트로 있었다. 어댑터가 라벨·값 구조만 읽었다. 같은 시기에 성분 쉼표 파싱을 고쳐 재실행하자 짧아진 결과의 끝쪽 이전 행이 DB에 그대로 남아(제품당 1~2행, 22개 제품), 해결률의 분모와 빈도표가 오염됐다.
- **원인**: "못 찾았다"를 "없다"로 단정하고 이미지 읽기로 넘어갔다(FP-C05의 변형). 저장 방식이 (제품, 순서) 키 덮어쓰기뿐이라 집합이 줄어드는 재처리를 고려하지 않았다.

## B에서 이식한 항목 (프로젝트 B `failure-patterns`의 번호)

### 외부 계약과 가짜 응답
- **B-FP-020 가짜 응답으로만 검증한 계약**: 외부 응답을 해석하는 코드는 실제 응답 1건으로 필드와 헤더를 확인한 뒤 그 형태를 픽스처로 쓴다. 코드와 가짜 응답이 같은 추측을 공유하면 틀려도 통과한다.
- **B-FP-022 가공한 파일로 원자료의 형태를 단정**: 응답의 형태에 대한 판단은 원본으로만 한다. 요약·집계·가공본은 근거가 아니다.
- **B-FP-023 외부 SDK가 같은 오류를 타이밍에 따라 다르게 감싼다**: SDK가 올려 준 예외 형태에만 기대어 분류하지 않는다. 전송 계층에서 요청 단위로 사실(전송 오류 종류, HTTP 상태 코드, `Retry-After`)을 직접 기록하고 그 사실을 예외 해석보다 먼저 쓴다. 비밀과 본문은 기록하지 않는다.
- **B-FP-050 설계 승인 전에 외부 계약을 실측하지 않음**: 위 "phase 설계 초안의 필수 항목" 1번. 성공 여부(exit 0·200)와 **반환 내용**을 따로 확인한다.
- **B-FP-076 합성 픽스처가 실제 산출물의 값을 가정으로 만듦**: 실제 실행 산출물을 읽는 코드의 픽스처는 실제 산출물의 키와 값 분포를 확인한 뒤 만든다.

### 테스트 작성
- **B-FP-061 고정 개수 단언**: 파일 수·항목 수를 `== N`으로 단언하지 않는다. **이름 집합**을 단언하고 새 항목을 만드는 step이 그 집합을 갱신한다. 출력의 위치(`[-1]`, 특정 줄 순서)도 단언하지 않는다.
- **B-FP-071 새 파일·새 키·새 이벤트가 기존 정확 일치 단언을 깸**: 새 파일, 새 응답 키, 새 이벤트, 새 상태를 만드는 step은 설계 때 `== {`, `== [`, `toHaveLength(`, `toEqual(`, `set(...) ==`, 파일 목록 단언을 검색해 깨지는 소비자를 찾고, 그 테스트를 step의 수정 허용 경로에 넣는다. 가능하면 `git clone --local` 복사본에 변경을 흉내 내 전체 테스트를 돌려 본다.
- **B-FP-060 닫힌 수정 파일 목록에서 소비자 테스트 누락**: step마다 바꾸거나 추가하는 심볼·파일·환경 변수·Makefile 타깃·문서 문구의 소비자 테스트를 찾아 수정 허용 경로에 "~에 한함, 단언 약화 금지" 형식으로 넣는다. 예외가 필요하면 단언을 느슨하게 하지 말고 예외 집합을 정확히 고정한다.
- **B-FP-012 동시 실행 결과의 순서를 단언**: 동시 실행의 단언은 결과의 집합·개수·불변식으로 한다. 순서를 단언하려면 코드가 순서를 보장하는 장치를 제공하는지 먼저 확인한다.
- **B-FP-011 무작위 실패를 입력 고정으로 덮음**: 무작위 입력에서만 나타나는 실패는 실제 결함을 먼저 의심한다. 난수·시간·`uuid`를 고정하는 테스트에는 사유 주석을 달고, 같은 입력의 무작위 대량 테스트(시드 고정, 건수 명시)를 함께 둔다.
- **B-FP-069 빈 집합에 대한 `all()`**: 검사 대상이 0건이면 실패로 처리한다. "검사한 것 0건, 실패 0건"은 통과가 아니다.
- **B-FP-073 SKIP 가능한 검사가 한 번도 실제로 돌지 않음**: 조건이 없으면 건너뛰는 검사는 결과에 실행 여부를 기록하고, 조건을 켠 실행을 마일스톤 안에 최소 1회 둔다.
- **B-FP-056 중간 step에서 완화한 테스트를 되돌리지 않음**: 테스트를 완화할 때는 복원 조건을 주석으로 남기고 그 조건이 해소되는 step에서 복원한다. 복원 뒤 실패하면 테스트를 고치지 말고 어느 항목이 명세와 다른지 보고한다.

### 환경과 설정
- **B-FP-030 빈 환경 변수가 기본값을 덮음**: 기본값이 있는 환경 변수는 한 함수로만 읽는다(미설정·빈 문자열·공백뿐이면 기본값). 필수 값은 누락이 드러나게 읽는다.
- **B-FP-032 로컬 통과가 CI 통과를 보장하지 않음**: git 이력, 파일 시스템, 시간, 입출력 지연에 기대는 테스트는 CI(얕은 복제, 느린 디스크)에서 달라질 수 있다고 본다. 실패는 재현한 뒤에 고친다(느린 입출력을 주입해 원래 테스트가 실패하고 수정 후 통과함을 확인).
- **B-FP-066 시간 제한 없는 대기**: CI 작업과 테스트에 시간 제한을 걸고(`pytest-timeout`), 외부 호출·스레드·서브프로세스 대기에는 항상 유한 대기를 둔다.
- **B-FP-051 첫 live에서 터질 것을 미리 따지지 않음**: 실행기는 시작 전에 환경(키 존재, 서비스 기동, 이미지 최신 여부)을 점검하고, 낡았으면 이유 코드를 출력하고 시작하지 않는다.
- **B-FP-072 작업 트리 복사가 비밀을 임시 폴더로 복사**: 작업 트리를 복사해 시뮬레이션할 때 `.env`와 추적되지 않는 데이터 폴더를 복사 대상에서 뺀다. `git clone --local` 복사본을 쓰면 추적되지 않는 파일이 자연히 빠진다.

### 평가와 판정
- **B-FP-043 기대값을 실행 뒤에 정함**: 기대값·가설·실행 계획은 실행 전에 정해 커밋한다. 실행기는 등록 파일이 커밋돼 있지 않으면 시작하지 않는다. 기록이 기대에 못 미치면 기대를 고치지 않고 실패로 표시한다. 새 등록은 기존 등록 파일을 고치지 않고 별도로 쌓는다. 이 프로젝트의 기준은 `docs/EVAL.md`에 동결돼 있다.
- **B-FP-040 0건 지표를 "아무것도 안 하기"로 통과**: 0이 좋은 지표(노출 0건)는 짝 지표와 함께 판정한다. 아무 일도 하지 않으면 0건이 되므로, 해야 할 일을 했는지(기대한 결과 수, 최종 상태)를 같이 본다. 테넌트 격리 검사에서는 정상 요청이 제대로 답을 받았는지가 짝 지표다.
- **B-FP-042 실행 중 코드가 정답지를 읽음**: 평가 대상 코드는 정답 파일에 접근할 수 없게 경로를 나눈다.
- **B-FP-044 같은 판정에 진입점이나 규칙 버전이 둘**: 같은 관측에 대한 판정은 함수 하나를 거치고, 규칙 버전은 필수 인자로 넘긴다. 규칙 버전은 실행 기록에 남긴다.
- **B-FP-045 세는 대상 정의가 다른 두 기록을 비교**: 두 기록을 비교하기 전에 양쪽이 세는 대상의 정의를 같게 맞춘다. 맞춘 뒤에도 진짜 불일치는 계속 잡히는지 테스트한다. 비교를 끄거나 허용 오차를 두지 않는다.

### 설계와 진행
- **B-FP-053 수정마다 새 phase**: 새 수정은 새 phase가 아니라 다음 계획된 phase의 step으로 넣는다.
- **B-FP-054·074 step 파일의 자기모순과 실행 전 점검 누락**: step마다 "수정할 파일" 목록을 적고, 그 목록을 금지사항과 작업의 모순, 계층 경계, 읽기 전용 목록과 대조한다. step 파일의 시그니처와 본문 요구가 서로 맞는지 본다. phase 실행 전 `git status`가 깨끗한지 확인한다.
- **B-FP-052 머지 후 사용자 실행 순서 누락**: PR 본문에 "머지 후 사용자 실행" 절을 두고 재빌드·재시작·키 갱신 필요 여부를 점검해, 필요하면 순서를 명령까지 적는다.
- **B-FP-063 규칙의 기계적 적용**: 전체 검증과 별도 PR을 건너뛰는 예외는 한 파일에 명시한 것만 인정한다. B에서는 실행 산출물인 비용 원장 하나뿐이었고, `docs/`와 결과 폴더는 테스트가 읽으므로 예외가 아니었다. 이 프로젝트의 예외 목록은 아직 없다.
- **B-FP-057 Stop hook이 실행 중인 phase의 중간 작업 트리를 검증해 세션을 막음**: 실행기가 도는 동안에는 `.harness/executing`(PID)이 있고 Stop hook은 검증을 건너뛴다. 실행 중에는 작업 트리, `scripts/`, `.claude/`, `phases/`를 건드리지 않는다.
- **B-FP-058 완료 신호 없는 실행 방식으로 대기**: `execute.py`는 종료 알림이 오는 방식(백그라운드 실행)으로 돌리고, 끝날 때까지 상태를 반복 조회하지 않는다.
- **B-FP-070 진입점이 시작 때 교체하는 의존성을 새 라우트가 생성 시점 값으로 붙잡음**: 새 API 라우트·의존성을 만드는 step은 실제 서버 진입점을 거치는 테스트를 최소 1개 둔다(`/harness` 설계 원칙 11번).
- **B-FP-075 사람이 보는 산출물을 직접 확인하지 않고 넘김**: 사람이 보고 판단하는 산출물은 합성 데이터로 실제 렌더링해(HTML은 브라우저 스크린샷, 가로 폭 지정) 가로 스크롤·줄바꿈·핵심 정보 표시를 확인한 뒤 넘긴다. 확인한 스크린샷 경로를 보고에 적는다.

## A에서 이식한 항목

- **A-FP-030 항목 하나의 실패가 배치 전체를 멈춤**: 소재 하나의 분석 실패는 기록하고 다음으로 넘어간다. 진행이 불가능한 경우만 전체를 멈춘다.
- **A-FP-033 멱등성 키와 출력 키 불일치**: 중복 제거 키는 결과를 결정하는 키와 같아야 한다(소재는 출처와 원본 ID).
- **A-FP-035 전송 후 실패를 재시도해 이중 과금**: 모델 호출 재시도는 503·429·연결 실패·시간 초과에만 한다.
- **A-FP-040 지시에 없는 네트워크 요청·다운로드**: 실제 API 호출과 다운로드는 step 파일에 명시된 것만 한다.
- **A-FP-041 세션 간 전달한 수정 요청이 반영되지 않음**: 여러 항목 요청은 항목별 반영 여부와 커밋을 보고하고, 검토는 이전 요청을 커밋과 대조한다.
- **A-FP-043 모호한 수량 기준**: 수량은 무엇을 세는지까지 적는다.
- **A-FP-044 측정 환경을 기록하지 않음**: 결과 문서에 날짜, 커밋, 모델 ID, 건수, 조건을 적는다.
- **A-FP-056 설정 로딩을 키 주입 테스트로만 검증**: 실제 `.env` 경로로 읽는 테스트를 두되 임시 `.env`를 쓴다.

## 하네스 강제 장치 (프로젝트 B에서 이식, 2026-11-12)

아래는 규칙이 아니라 기계가 검사하는 것이다. 테스트는 `make verify`에 포함시킨다(`pytest`의 `testpaths`에 `scripts`).

- `scripts/step_file_checks.py`: step 파일의 열람 금지·실행 금지 대상·수정 허용 경로 검사와 소비자 테스트 경고. 이 저장소는 첫 phase부터 전부 대상이다.
- `scripts/test_step_files.py`: 모든 step 파일에 공통 금지사항 블록이 수정 없이 들어 있는지, 형식 v2 검사를 통과하는지.
- `scripts/execute.py`: 실행 전 작업 트리 청결 검사, `.harness/executing` 잠금.
- `scripts/hooks/verify-before-stop.sh`: 실행 중에는 검증을 건너뛰고, 예외 경로만 바뀐 경우 건너뛴다.
- `scripts/exempt_paths.json`: 검증 없이 넘어갈 수 있는 실행 산출물 경로(정확히 1개). B의 값(`data/manifest/costs.jsonl`, 비용 원장)을 그대로 뒀다. 이 프로젝트의 비용 기록 경로가 정해지면 맞춘다.
- 린트 설정에서 `scripts`와 `phases`는 제외한다(B의 `extend-exclude`와 같게).
